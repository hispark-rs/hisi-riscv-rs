1//! # hisi-hal — Hardware Abstraction Layer for HiSilicon WS63 (RISC-V).
2//!
3//! A comprehensive HAL providing safe, idiomatic Rust APIs for all WS63
4//! peripherals. Modeled on esp-hal patterns with typed GPIO drivers, audited
5//! clock metadata, typed identities, and embedded-hal trait implementations.
6//!
7//! ## Clock gating
8//!
9//! Most peripherals need their CLDO_CRG clock gate enabled before register
10//! access. The gates default to enabled out of reset; `clock_init::init_clocks()`
11//! sets up the system clocks for firmware that does not boot through flashboot.
12//! Constructors like `I2c::new_i2c0()`, `Uart::new_uart0()`, and `Watchdog::new()`
13//! write configuration registers immediately. WDT/RTC/TCXO are always-on.
14//!
15//! ```ignore
16//! // Illustrative shape only (`system`/`peripherals` stand in for your tokens):
17//! let clocks = clock_init::init_clocks(&system.sys_ctl0, &system.cldo_crg);
18//! // Now safe to construct peripheral drivers
19//! let uart = Uart::new_uart0(peripherals.UART0, Config::default());
20//! ```
21//!
22//! ## MSRV
23//!
24//! The minimum supported Rust version is **1.88** (declared as `rust-version` in
25//! `Cargo.toml` — bumped from 1.85 for the `instability` crate). An MSRV bump is a
26//! minor-version change, not a patch.
27// `no_std` for firmware builds; `std` is linked under `cfg(test)` ONLY on the
28// host so the lib unit tests can use the standard test harness (run via
29// `cargo test --target x86_64`). On the RISC-V target the lib stays `no_std`
30// even under the `test` cfg: `cargo test --target riscv32imfc-...` builds the
31// lib-test target too (alongside tests/hil.rs), and `std`/`test` don't exist on
32// the bare-metal target — the host-only unit-test modules are themselves gated
33// `#[cfg(all(test, not(target_arch = "riscv32")))]`, so they vanish there.
34#![cfg_attr(not(all(test, not(target_arch = "riscv32"))), no_std)]

47// Exactly one chip must be selected (each pulls its PAC + soc/<chip>.rs). There is
48// NO default chip (esp-hal style) — every consumer names one explicitly.
49#[cfg(all(feature = "chip-ws63", feature = "chip-bs21"))]
50compile_error!("hisi-hal: select exactly ONE chip feature — `chip-ws63` OR `chip-bs21`, not both.");
51#[cfg(not(any(feature = "chip-ws63", feature = "chip-bs21")))]
52compile_error!(
53    "hisi-hal: no chip selected — enable exactly one chip feature, e.g. \
54     `features = [\"chip-ws63\"]` (WS63) or `features = [\"chip-bs21\", \"unstable\"]` (BS2X). \
55     There is no default chip."
56);
57#[cfg(all(feature = "chip-bs21", not(feature = "unstable")))]
58compile_error!(
59    "hisi-hal: BS2X support is experimental; enable `unstable` with \
60     `features = [\"chip-bs21\", \"unstable\"]`."
61);

205// BS2X-enabled shared drivers (`pwm`, `spi`, `wdt`, `ulp_gpio`). These are not
206// per-module soft-gated, but the whole `chip-bs21` target is hard-gated by
207// `unstable` above until BS2X silicon HIL exists. They build for BS2X because
208// (a) the driver code is chip-neutral (it goes through `crate::soc::pac` aliases),
209// (b) their peripheral instances are in both `Peripherals` structs, and (c) BS2X
210// uses the SAME IP version as WS63 — PWM v151, SPI v151, WDT v151 (the fbb_bs2x
211// vs fbb_ws63 `*_regs_def.h` headers are byte-identical bar copyright comments),
212// and `ulp_gpio` reuses the GPIO v150 block that regular `gpio` already drives on
213// BS2X (blinky). So the register layout is verified, not guessed. What's guaranteed
214// today is a register-correct, compiling blocking API.
215//
216// Still chip-ws63-only (different IP version or no BS2X peripheral): i2c (v150 vs
217// BS2X v151), rtc (v100 vs v150), lsadc (v154 vs v153), i2s/sfc (no BS2X instance),
218// and the clock/crypto/system stack (deeper port).
219/// PWM driver (v151) with typed `PwmPeriod`/`Duty` config.
220pub mod pwm;
