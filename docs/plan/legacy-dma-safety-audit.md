# WS63 / BS21 旧 DMA guard 安全审查

状态：**未修复，禁止把旧传输 guard 描述为已证明内存安全**。本记录针对
`hisi-hal` 的旧 `src/dma.rs`，不推断 WS53 `dma_ws53.rs` 有同样的行为。
本轮未操作板卡，也没有证明控制器总线事务的完成语义。

## 已从源码确认

1. `quiesce_channel` 在有限次数内等待 `active`，超时仍执行 disable 并返回。
   `Transfer::wait` 和两种 guard 的 `Drop` 之后可以释放或归还缓冲区及通道。
   因此软件没有证明该时刻停止访问内存；现有“provably stopped”“UAF
   unrepresentable”等说明超出源码能够支持的范围。
2. 通用 `embedded_dma` 缓冲区可携带非静态借用。安全代码可遗忘 guard，
   跳过其 `Drop`；仅靠 guard 保存借用不足以保证原缓冲区一直可供硬件访问。
3. WS63 在目标区完成或超时后按缓存行失效。接口只建议对齐，并未证明
   目标区首尾整个缓存行没有其他脏数据；失效可能丢弃相邻数据。
4. WS63 外设路径接受由调用方提供的地址、宽度及路由，需单独审计其
   类型和权限约束。不能把普通地址的数值有效性等同于设备及总线权限。
5. 旧外设入口使用 `u8` 缓冲区长度作为 DMA beat 数，却允许选择半字 beat；
   这会使传输字节数与缓冲区大小不一致，可能越界。

## 关闭条件

- 核对 WS63 / BS21 各自 SDK 和控制器证据，区分 channel enable、active、
  总线未完成事务及外设排空；在无 drain 证据时保留通道和缓冲区，不能
  以超时或禁用位变化作为归还许可。
- 设计对 `mem::forget` 仍成立的生命周期和所有权契约，及非一致性缓存
  完整行的资源约束；不把未经证明的前提简单包装成安全 token。
- 逐项审查内存、外设 TX/RX、失败恢复和掉电边界；为可复用的状态逻辑
  提供主机并发/错误注入测试，再按实际条件做 QEMU 与实板验证。
- 旧 `unstable` 接口如果调整，必须同步示例及消费者，明确兼容性与迁移；
  已发布的稳定 API 不得无故破坏。修复前不要新增依赖旧 guard 安全保证的
  示例，不将既有实板的正常完成结果当作取消/超时安全证明。

源码基线：HAL `3adeac4`；相关路径为 `start_mem_to_mem`、
`start_mem_to_peripheral`、`start_peripheral_to_mem`、`Transfer::wait`、
`PeripheralTransfer::wait`、`quiesce_channel` 和两个 `Drop` 实现。

## 进展：静态借用限制

HAL `e5c12b6` 为上述三个实验性启动入口添加 `'static` 缓冲区类型约束，
阻止把非静态借用的栈空间交给一个可被遗忘的 guard。外部消费者的栈借用
用例实际得到 E0521，相关 compile-fail 文档测试通过；两旧芯片相关主机
测试、三芯片 RISC-V Clippy 和 BS21 示例 workspace 检查通过。这个约束会
改变实验接口对非静态借用的接受范围；已有 WS63 示例的静态缓冲形式无需
改写，但其 workspace 检查因离线缓存缺少 `hisi-panic-handler` 尚未完成。

这只是第 2 项的一部分：不能证明 owned buffer 的提前释放路径或取消后的
总线排空，也不解决第 1、3、4 项。仍不得把旧 guard 作为安全修复完成。

## 进展：帧宽和缓存范围

HAL `725c890` 拒绝旧 WS63 字节缓冲外设入口的半字帧，避免把字节长度
误作半字次数；未来半字支持须以类型化缓冲和正确数量单独实现。HAL
`25ee689` 要求 WS63 接收目标起始地址和长度均为非零完整缓存行且不溢出，
失败发生在 DMA/MMIO 操作之前。主机测试覆盖两方向半字拒绝、缓存对齐、
空范围和溢出，三芯片目标 Clippy 通过。

这两项改变旧实验接口的可接受配置，不能证明总线排空、控制核或其他
主设备不会访问同一内存，也没有实板验证。完整缓存生命周期和地址/路由
权限仍须审计；`active` 等待超时后的资源释放问题仍未解决。

## 进展：外设地址边界

HAL `b743851` 将 WS63 的两个实验性外设传输入口改为 `unsafe`，明确要求
调用者证明地址、请求路由、设备所有权、缓存和独立总线排空。直接安全调用
现在无法通过编译，不能把整数地址视为已验证的设备 token。主机测试、
compile-fail 文档和三芯片目标 Clippy 通过；现有仓库未发现这些入口的
非测试调用者。这是实验接口的调用方式变更，不证明硬件前提已满足。

内存到内存启动仍是安全接口，取消后归还及通道重新启用等路径仍须处理；
不能因为外设入口增加 `unsafe` 就声称 DMA 子系统安全或问题已解决。

## 进展：空传输和 SDK 停用证据

HAL `a90daf7` 在内存及外设传输入口拒绝零长度，先于控制器和 DMA 寄存器
访问；两旧芯片 DMA 相关主机测试及三芯片目标 Clippy 通过。此行为不推断
硬件零长度语义，也不修复尚未证明的排空或资源归还。

本机 WS63 SDK `bffc3560e480970a9e84707e0abdcc24e682d4f3` 的未修改文件
`src/drivers/drivers/hal/dma/v151/hal_dmac_v151.c` SHA-256
`622cc523713a184f84b56fd90f53a4f8dd7e70c7e2c85e43fece144d1d412782`：
`hal_dma_v151_enable(..., false)` 清通道使能、释放握手及链表；它没有提供
可用于证明已发总线写完成的等待或屏障。`hal_dmac_v151_regs_def.h`
SHA-256 `954a30deba7fa311be9ab779dc7258e4363094cf905949a9fa94866fb4699af4`
只命名 `active` 和 `halt` 位，未定义其排空语义。该 SDK 树有其他本地改动，
上述两文件经 diff 检查未修改；不能以此推断芯片实际总线完成行为。

## 进展：等待超时保留资源

HAL `fcc72ff` 在旧内存传输等待超时后尝试停止，但将驱动、通道和缓冲区
保留于错误对象；丢弃错误对象也保留它们，不对可能仍在写入的目标做缓存
失效。仅允许调用者在独立证明硬件/总线排空后通过 `unsafe into_parts`
取回。WS63 外设传输的超时分支同样保留 guard 和资源，当前没有恢复句柄，
因此会永久占用这些资源。此更改调整实验接口的错误恢复方式。

主机测试直接验证错误对象丢弃时资源不析构以及显式恢复后析构，文档
compile-fail 和三芯片 Clippy 通过；该测试未模拟完整 MMIO 超时时序或
物理排空。正常完成、提前 `Drop`、通道重新启用及驱动借用生命周期仍未
解决，不能把这项超时防护视为完整 DMA 内存安全修复。

## 进展：提前丢弃保留资源

HAL `5b0b719` 把旧内存和 WS63 外设 guard 持有的驱动、通道和缓冲区改为
显式保留；提前 `Drop` 只尝试停止而不析构这些资源，也没有恢复句柄。主机
测试让停止过程在访问 MMIO 前因无效通道 panic，确认展开时缓冲区仍未析构；
两旧芯片 DMA/文档测试和三芯片目标 Clippy 通过。此测试不模拟真实停止、
总线或缓存，永久占用是当前的保守行为。

这没有解决正常完成后通过安全 `wait` 归还资源的硬件排空证明，也没有解决
外部重启通道、其他总线主设备或被借用的驱动 token 可能重新获得的问题。
现有安全内存启动接口仍需进一步调整，不能宣称整个 DMA guard 安全。

## 进展：停止状态诊断

HAL `6b30c76` 在内存传输等待超时后的错误对象中记录停止轮询观察：
`ActiveClear` 为禁用前读到活动位清零，`ActiveDeadline` 为有限轮询期间
活动位持续置位。两种结果均继续保留资源，均不证明总线排空。通过内部
寄存器接口的主机故障注入验证先 halt、轮询再 disable，以及两种结果；
两旧芯片主机和文档测试及三芯片目标 Clippy 通过。实际寄存器时序和
硬件状态含义仍未验证，正常完成、驱动借用和通道重启风险仍未关闭。

## 进展：旧配置的显式重启边界

HAL `7551094` 将实验性 DMA 模块的 `enable_channel` 和 `resume_channel`
改为 `unsafe`。通道 token 不证明残留寄存器中的地址、链表或缓冲区仍然
有效；调用者必须证明资源、路由、缓存及总线排空条件。源码搜索未发现
仓内调用者；WS63 38 项、BS21 22 项 DMA 主机测试、两芯片编译失败文档
测试和三芯片 RISC-V Clippy 通过，使用父仓本地集成依赖并非独立发布验收。

这只是消除了两个直接的安全重启入口：正常完成的总线排空、控制器
重新启用以及驱动借用的生命周期仍无证明，也没有实板验证。不应据此
宣称 DMA guard 已经安全。
