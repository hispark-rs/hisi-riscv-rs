# WS63 W2E-H PKE P-256 Evidence - 2026-07-17

## Scope

This evidence covers P-256 affine point multiplication, point addition, and
fixed-prime field multiplication/squaring used by the pinned upstream hostap
SAE path. It does not claim that the entire Dragonfly exchange or every P-256
primitive is hardware-backed.

The protocol state machine remains in hostap. Rust serializes the selected
affine point and scalar through the narrow fallible `TryP256PointMul` contract,
then validates the returned point before handing it back to hostap. A hardware
error aborts the operation; there is no silent RustCrypto fallback.

## Hardware Boundary

- `hisi-crypto-ws63` owns PKE locking, instruction dispatch, bounded polling,
  Montgomery parameters, PKE DRAM clearing, and error propagation.
- The HAL exposes only the unique `Pke` peripheral token. It does not expose a
  second SHA/ECC/signature algorithm API.
- The RF integration injects PKE explicitly and shares the outer runtime mutex
  with the other WS63 crypto engines.
- Temporary scalar, coordinate, and output buffers are zeroized.
- The current implementation accelerates point multiplication, affine point
  addition, and fixed-prime field multiplication/squaring. Doubling is
  explicitly mapped to scalar multiplication by two; validated inverse inputs
  return the group identity without inventing affine sentinel coordinates.
  Field inputs are canonical `< p` values rather than unrestricted bignums.
  Remaining SAE arithmetic stays in the explicit software portion of the mixed
  profile.

## ROM-RAM Diagnosis

The first on-silicon SAE attempt faulted at `0xac0f0000` after the startup PKE
known-answer test had passed. Stack and disassembly evidence traced the call to
a stateful ROM PKE helper which obtains the CPU identity through a callback
table rooted at fixed ROM-RAM address `0x00a024cc`. After RF initialization,
that location contained legitimate standalone application data and the ROM
helper jumped through the colliding value.

The original complete vendor firmware links the matching security driver and
owns that private RAM contract. A standalone Rust image does not. The corrected
backend therefore does not call ROM entries which depend on that private state.
It drives lock, noise control, work length, instruction selection, batch start,
finish polling, Montgomery setup, and DRAM clear through PAC registers. Only
stateless ROM helpers for PKE RAM copies and curve-parameter loading remain.

This is an ownership boundary, not a delay or reset workaround. Stateful ROM
PKE entries remain hidden from the public `hisi-rom-sys-ws63` contract.

### Point-addition follow-up

The next narrow capability is `TryP256PointAdd`. Its result type explicitly
distinguishes an affine point from infinity, because affine coordinates cannot
encode the identity element. The WS63 backend uses the vendor PKE instruction
sequence only for distinct affine inputs. The first on-silicon KAT intentionally
tested `G + G` and returned a mismatch: the audited add instruction does not
cover doubling. The implementation therefore dispatches equal points to the
already verified hardware scalar-multiplication-by-two path. Two validated
points with the same x coordinate and different y coordinates are inverses and
return infinity. No hardware error falls back to RustCrypto.

The corrected KAT covers all three paths:

- `G + G = 2G` through hardware scalar multiplication;
- `G + 2G = 3G` through the PKE affine-add instruction;
- `G + (-G) = infinity` through the explicit identity result.

The guarded link again verified 1,157 layout sections, patched 4,127 vendor
relocations, generated 37 mask-ROM patches, and sealed the final ELF hash. A
3 MHz probe-rs download completed with full verify in about 92 seconds. The
first complete boot then passed SAE, required PMF, EAPOL, DHCP, gateway/public
5/5 ping, and lease renewal. Its PKE snapshot reported nine point operations,

### Fixed-prime field follow-up

The next narrow capability is `TryP256FieldMul`. The contract fixes the NIST
P-256 base-field prime in the type and accepts only canonical 32-byte operands;
it does not expose a generic modular-arithmetic provider. The software oracle
and WS63 backend share known-answer tests for generator-coordinate multiply and
square. Hardware failures remain fallible and never select RustCrypto.

The first on-silicon field KAT returned backend error `0xffff0305`. Comparing
the selected ROM instruction range with the vendor driver showed that
`rsa_mul_mod()` first calls `update_rsa_modulus()`, which computes and writes
Montgomery `R^2 mod p` into PKE section 32. The six selected instructions then
consume that section to transform both operands before multiplication. The
fixed-prime backend now writes the already verified P-256 `R^2` constant
explicitly. This reproduces the required hardware state without calling the
stateful ROM helper or widening the public contract.

The corrected startup KAT and a full WPA3 smoke passed. The smoke performed 144
field operations (139 multiply, 5 square), zero failures, with a 1 ms observed

### Confirmed-disconnect ordering follow-up

An intermediate zeroization-only rebuild still produced one failure in 20
resets. That run completed SAE and received an association-success response,
but no first EAPOL frame reached hostap; after the bounded watchdog it ended in
`SCANNING`. PKE field, point, TRNG, event-ring, and authentication-response-2
diagnostics all remained clean.

The remaining race was in the recovery adapter. The confirmed-disconnect
callback called `wpa_supplicant_associate()` in the same callback stack as
`EVENT_DISASSOC`, allowing the pending disconnect state transition to overwrite
the new association. `ws63-radio-sys` commit `fc3f404` now registers zero-delay
eloop owner work instead. This is an ordering boundary, not an arbitrary sleep:
the cached-BSS association begins only after the current event stack unwinds.
Registration failure is fail-closed, and explicit disconnect cancels pending
owner work.

The final integration is recorded by `hisi-crypto` commit `ee7ab87`,
`hisi-crypto-ws63` commit `e6d9378`, examples commit `76b282b`, and parent
commits `e2ccf4e92` / `126ce8544`. A fully verified 3 MHz download took 92.62
seconds after one separately classified probe-rs page-write/DMI transport
failure and official-FWPKG recovery. The final single smoke completed WPA3,
required PMF, EAPOL, DHCP, gateway/public 5/5 ping, and lease renewal.

The same image then ran 20 nRST cycles. Every cycle deliberately exercised the
