# WS63 W2E-H PKE P-256 Evidence - 2026-07-17

## Scope

This evidence covers P-256 affine point multiplication used by the pinned
upstream hostap SAE path. It does not claim that the entire Dragonfly exchange
or every P-256 primitive is hardware-backed.

The protocol state machine remains in hostap. Rust serializes the selected
affine point and scalar through the narrow fallible `TryP256PointMul` contract,
then validates the returned point before handing it back to hostap. A hardware
error aborts the operation; there is no silent RustCrypto fallback.

## Hardware Boundary

- `hisi-crypto-ws63` owns PKE locking, instruction dispatch, bounded polling,
  Montgomery parameters, PKE DRAM clearing, and error propagation.
- The HAL exposes only the unique `Pke` peripheral token. It does not expose a
  second SHA/ECC/signature algorithm API.
- The RF integration injects PKE explicitly and shares the outer runtime mutex
  with the other WS63 crypto engines.
- Temporary scalar, coordinate, and output buffers are zeroized.
- The current implementation accelerates point multiplication only. Remaining
  SAE arithmetic stays in the explicit software portion of the mixed profile.

## ROM-RAM Diagnosis

The first on-silicon SAE attempt faulted at `0xac0f0000` after the startup PKE
known-answer test had passed. Stack and disassembly evidence traced the call to
a stateful ROM PKE helper which obtains the CPU identity through a callback
table rooted at fixed ROM-RAM address `0x00a024cc`. After RF initialization,
that location contained legitimate standalone application data and the ROM
helper jumped through the colliding value.

The original complete vendor firmware links the matching security driver and
owns that private RAM contract. A standalone Rust image does not. The corrected
backend therefore does not call ROM entries which depend on that private state.
It drives lock, noise control, work length, instruction selection, batch start,
finish polling, Montgomery setup, and DRAM clear through PAC registers. Only
stateless ROM helpers for PKE RAM copies and curve-parameter loading remain.

This is an ownership boundary, not a delay or reset workaround. Stateful ROM
PKE entries remain hidden from the public `hisi-rom-sys-ws63` contract.

## Verification

- `hisi-crypto`, `hisi-rom-sys-ws63`, and `hisi-crypto-ws63` host tests passed;
  the WS63 backend ran 12 tests with all features.
- RV32 check and clippy with warnings denied passed for `hisi-crypto-ws63` and
  the upstream WPA3 RF profile.
- The guarded two-pass link passed with 1,157 layout sections, 4,127 vendor
  relocations, and 37 mask-ROM patches.
- The on-silicon generator-times-one P-256 KAT passed before RF init.
- A fully verified 3 MHz probe-rs download completed in about 85 seconds; J-Link
  nRST then produced WPA3+PMF, EAPOL, DHCP, ARP, lease renewal, and ping markers.
- The successful smoke used four PKE requests, zero failures, about 20 ms total,
  and a 7 ms observed maximum.

The unchanged image then ran 20 nRST trials:

- all recorded PKE operations completed with zero PKE failures and no exception;
- the observed per-operation maximum was 7-8 ms;
- `WLAN_AUTH_RSP2_TIMEOUT` was zero;
- association completed in 19/20 runs;
- public ICMP returned 91/95 replies and gateway ICMP returned 90/95 replies.

The one failed association run completed SAE and received an association-success
response, but received no first EAPOL frame. It performed seven successful PKE
requests and reached neither EAPOL nor key installation. This is the existing
association-success/no-first-EAPOL recovery tail, not evidence of PKE failure.
The local matrix is under
`/private/tmp/ws63-pke-wpa3-reset-matrix-20260717`; it is diagnostic evidence,
not a checked-in secret or long-term runner artifact.
